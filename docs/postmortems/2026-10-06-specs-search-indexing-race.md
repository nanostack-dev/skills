> Blameless: this document names systems, processes and missing guards, not people.

## Summary

The routine extended `echopoint: specs` to cover spec search (echopoint#508) with three search nodes that ran right after `create-spec`. Spec search documents are written by a queued sync job after the create commits, not inside it, so a search that lands before the job finds nothing. The third repeat run in the dev org did exactly that: `search-slug` saw an empty result while the two searches that ran a few milliseconds later found the spec. The flow now waits through a poll module (`specs: search poll (module)`) until the slug is searchable, then runs the searches; it passed three times in each org, and one dev run needed a retry, which shows the lag is real. The flow-suite-testing skill now says that a read of a projection polls.

## Impact

One failed authoring run of `echopoint: specs` in the dev org. The racy definition was saved to the CI-tagged flow in both orgs for about six minutes; no scheduled or CI suite run used it.

- **1** failed run (dev org)
- **~6 min** racy definition live
- **0** CI or scheduled runs affected

## Trigger

The updated `echopoint: specs` definition, with search nodes wired straight after `create-spec`, was saved to the CI org and then mirrored to the dev org.

## Detection

The authoring loop's third repeat run in the dev org failed on `search-slug` (`JSONPath '$.groups[0].items[*].identifiers.spec_slug' did not match any nodes`). Three CI-org runs and two dev-org runs had passed, because the job usually lands first.

## Resolution

A poll module searches by the run's slug every 500 ms (30 s budget) until the spec is found; `search-slug`, `search-partial-slug` and `search-title` run after it. Both orgs were updated, validated and run three times each, all green. Two first attempts at the module failed on runner mechanics (a `{{$runId}}` in a module binding, a JSONPath into a final output); those lessons are in the skill too.

## Root causes

- **R1** No document a test author reads states that search results lag writes; the CT helper polls, but only its code shows it
- **R2** The flow-suite-testing skill did not say that a read of a projection waits through a poll
- **R3** The repeat-run gate samples an idle API; a CI burst slows the worker, so the gate under-samples the race the suite will meet

## Contributing factors

- The generator updates the tagged flow in place, so the new definition is in the suite as soon as it is saved.
- Building the poll took two more tries: a `poll` body sees only flow inputs, a `{{$runId}}` in a module binding resolves in the child, and JSONPath does not descend into a final output. None of this was written down.

## Lessons learned

### What went well

- The three-run gate in a second org caught the race before any CI run used the definition.
- The sibling searches in the failing run found the spec, which pointed at timing rather than at the search query within minutes.

### What went wrong

- The commit message of the feature under test was trusted over its code; the enqueue was in plain view in `search_sync.go`.
- The first two poll modules were written without reading how a `poll` body gets its inputs.

### Where we got lucky

- The race showed in the sixth run. On an idle API it could have passed all six and first failed in CI under a burst, where it reads as a regression of #508.
- No other flow in the suites asserts on search right after a write; `echopoint: catalog and org` only checks that the flows domain is non-empty.
